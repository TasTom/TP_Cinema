### A01 — La précision du total ne couvre pas les prix autorisés

Preuve : création d'une séance au prix de **99 999 999,99** acceptée en **201**, puis réservation
de huit places refusée en **409 `CONFLIT_DONNEES`**. Le montant calculé est **799 999 999,92**,
qui dépasse `DECIMAL(10,2)`. Le journal SQL confirme un dépassement de `montant_total`.
Aucune réservation partielle ne subsiste.

Origine : [SeanceRequest](../src/main/java/fr/butinfo/cinema/seance/api/dto/SeanceRequest.java)
autorise huit chiffres entiers pour le prix ; le
[schéma](../src/main/resources/db/migration/V1__schema_initial.sql#L52) et
[Reservation](../src/main/java/fr/butinfo/cinema/reservation/Reservation.java#L47) utilisent
la même précision pour le total que pour le prix unitaire.

Correction recommandée : ajouter une **nouvelle migration** élargissant `montant_total` à une
précision couvrant huit fois le maximum unitaire, au minimum `DECIMAL(11,2)`, et aligner le mapping
JPA. Ne pas modifier une migration V1 déjà appliquée. Tester le maximum et huit places ensemble.

### A02 — La conversion JSON précède et contourne la validation entière

Preuves HTTP :

- `nombrePlaces: 1.9` produit **201**, avec `nombrePlaces: 1` et le montant d'une seule place ;
- un `seanceId` écrit sous la forme `N.9` produit **201** pour la séance entière `N`.

`@Min` et `@Max` voient la valeur entière après conversion ; ils ne détectent donc plus la
fraction envoyée. Il ne s'agit pas d'une surréservation, mais d'une modification silencieuse
du sens de la demande, y compris de la ressource ciblée.

Origine : types `Integer` et `Long` des DTO, combinés à la coercition JSON par défaut ; aucune
configuration de rejet des nombres flottants vers ces types.

Correction recommandée : rejeter explicitement cette coercition dans la configuration Jackson 3,
en conservant les DTO immuables. Ajouter des cas sur quantité, identifiants, durée et capacité.
La politique concernant les chaînes numériques peut être décidée séparément.

### A03 — Le verrou protège les données mais pas le contrat d'erreur

Preuve : maintien d'un verrou SQL sur une séance, demande de réservation concurrente et
`innodb_lock_wait_timeout=6` pour les connexions de test. Réponse observée :
**500 `ERREUR_INTERNE`**, causée par `CannotAcquireLockException`. Aucune réservation n'est créée.

Origine : [GlobalExceptionHandler](../src/main/java/fr/butinfo/cinema/common/error/GlobalExceptionHandler.java#L125)
ne distingue pas l'échec du verrou de l'erreur technique générique. Le scénario normal à deux
réservations reste correct : il ne faut pas confondre ce défaut de traduction HTTP avec un
dépassement de capacité.

Correction recommandée : traduire les conflits de verrouillage attendus en **409**, avec un code
métier stable, sans exposer leur cause SQL. Distinguer ce cas d'une base réellement indisponible.
Le délai de six secondes est une configuration de test, pas le délai configuré en production.

### A04 — Le frontend contredit la lecture littérale de la règle sur les mots de passe

Preuve : `GET /login` expose les trois mots de passe, également écrits dans
[login.html](../src/main/resources/templates/login.html#L40), sous `src/main/resources`.
Les comptes de `SecurityConfig` utilisent bien BCrypt et les vrais identifiants ont été testés.
Il ne s'agit pas de secrets de production découverts : ce sont les comptes fictifs documentés.

Le PDF demande de documenter ces comptes dans le **README**, tout en interdisant le stockage en
clair dans le code source. L'affichage ajouté dans le template est donc un écart à traiter par
prudence avant remise, sans prétendre connaître l'interprétation du correcteur.

Correction recommandée : retirer les mots de passe du template et renvoyer vers le README.
Conserver les hachages dans la configuration. La nécessité des identifiants fictifs dans les
tests d'authentification est distincte de leur publication dans une ressource applicative.

### A05 — La gestion centralisée ne couvre pas tous les chemins HTTP

Preuves :

| Requête | Observé | Attendu ou limite |
|---|---|---|
| POST réservation avec `Content-Type: text/plain` | **500 `ERREUR_INTERNE`** | **415**, erreur de client |
| GET `/api/absent`, authentifié | **404**, JSON Boot avec `error`, sans `code` | 404 avec le contrat d'erreur annoncé |
| PUT `/api/films`, authentifié | **405**, JSON Boot avec `error`, sans `code` | Statut correct, contrat différent |
| GET films avec `Accept: application/xml` | **406**, corps vide | Négociation HTTP respectée ; ce résultat ne prouve pas une fuite |

Origine : l'advice est sélectionné par
[`@RestControllerAdvice(annotations = RestController.class)`](../src/main/java/fr/butinfo/cinema/common/error/GlobalExceptionHandler.java#L29).
Il ne couvre pas de la même manière les erreurs de routage et de ressources statiques. Son
gestionnaire générique transforme aussi le type de corps non pris en charge en erreur serveur.

Correction recommandée : conserver les statuts des exceptions HTTP du framework et prévoir une
réponse d'erreur API pour les erreurs de routage, en préservant les pages HTML de l'interface.
Ne pas supprimer aveuglément le sélecteur de l'advice : cela toucherait les contrôleurs Thymeleaf.
Ne pas forcer une réponse JSON quand la négociation la refuse explicitement.

### A06 — Les métriques surcomptent des transitions métier

Deux reproductions indépendantes :

1. Deux annulations de la même réservation sont mises en attente du verrou de séance, après
   lecture de l'état confirmé. Les deux répondent **204**, mais le compteur `annulee` augmente
   de **2** au lieu de **1**. Deux attentes SQL ont été constatées avant libération du verrou.
2. Une création dans une transaction extérieure explicitement annulée laisse **0 réservation**
   en base, mais incrémente le compteur `confirmee` de **1**.

Origine : [ReservationService](../src/main/java/fr/butinfo/cinema/reservation/ReservationService.java#L70)
lit la réservation avant le verrou et conserve son état chargé ; les métriques sont émises
[avant la validation de la transaction](../src/main/java/fr/butinfo/cinema/reservation/ReservationService.java#L60).
Le test existant de double annulation est séquentiel et réutilise le même objet Mockito.

Correction recommandée : rendre la transition conditionnelle sur l'état relu/verrouillé en base,
et publier les métriques de confirmation/annulation **après commit**. Une simple seconde lecture
JPA peut retrouver l'objet déjà présent dans le contexte de persistance : prévoir un véritable
rafraîchissement ou une mise à jour conditionnelle. Garder un ordre de verrouillage cohérent.
Les refus de capacité restent des événements de tentative, distincts d'une écriture validée.

L'invariant de capacité reste préservé dans ces reproductions ; c'est le bonus d'observabilité
qui manque de cohérence dans ces cas.

### A07 — Une borne de date peut déborder avant la requête SQL

Preuve : `GET /api/seances?au=%2B999999999-12-31` produit **500 `ERREUR_INTERNE`**.
La valeur est convertible en `LocalDate`, puis
[`au.plusDays(1)`](../src/main/java/fr/butinfo/cinema/seance/SeanceService.java#L47) déborde.

Correction recommandée : borner les dates supportées par l'application et le stockage, et traduire
les bornes invalides en **400** avant le calcul de fin exclusive. Les autres dates extrêmes et les
bornes SQL n'ont pas toutes été testées : ne pas généraliser une correction au seul exemple observé.

### A08 — Le healthcheck du conteneur ne prouve pas que les identifiants fonctionnent

Preuve en lecture : `mysqladmin ping` avec un mot de passe volontairement incorrect affiche
`Access denied` tout en terminant avec le **code 0**. Le healthcheck utilise justement cette
[commande](../docker-compose.yml#L18), avec les identifiants codés en dur.

Conséquence : un état Compose `healthy` indique que le serveur répond, pas que le compte
applicatif peut exécuter une requête. Changer seulement les identifiants du healthcheck ne
renforce donc pas suffisamment ce contrôle.

Correction recommandée : utiliser une requête authentifiée légère telle que `SELECT 1` avec les
variables du conteneur. Conserver aussi la vérification de santé applicative. Cette limite
n'invalide pas les migrations et lectures réelles réussies avec les identifiants actuels.

## Sécurité : contrôles positifs et limites de production

Les onze sondes MVC de sécurité réussissent : vrais identifiants BCrypt CLIENT et ADMIN acceptés,
PROGRAMMATEUR refusé sur la réservation, mauvais mot de passe et compte inconnu en 401, session
web non réutilisée pour authentifier l'API, CSRF sur connexion et déconnexion, en-têtes `nosniff`
et `DENY`, aucune autorisation CORS arbitraire sur la requête contrôlée.

Les sondes MySQL/HTTP confirment également : montant et statut supplémentaires envoyés par le
client ne remplacent pas le calcul serveur, et un titre contenant un script est échappé dans le
catalogue. Les requêtes de recherche utilisent des paramètres liés ; aucune concaténation SQL
de valeur utilisateur n'a été relevée dans les repositories inspectés.

### Propriété des réservations

Un second compte CLIENT ajouté uniquement dans le contexte de test annule une réservation du
premier compte : **204**. Le modèle ne relie pas une réservation à un utilisateur authentifié.
Le code de réservation fonctionne donc comme une information nécessaire à l'annulation.

Le PDF impose des rôles, **pas une règle explicite de propriété** : ce point n'est pas présenté
comme un échec de recette. Pour une vraie billetterie multi-utilisateur, définir le propriétaire
et son contrôle d'accès devient nécessaire. Une référence difficile à deviner ne remplace pas
ce contrôle ; voir la [référence OWASP sur les autorisations par objet](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/).

### HTTP Basic, CSRF et exposition réseau

HTTP Basic est imposé par le sujet. Son utilisation sur HTTP local, les comptes fictifs publics,
`useSSL=false` vers MySQL et le port MySQL publié sur toutes les interfaces sont des choix de
démonstration à revoir avant un déploiement réel. Aucun contournement distant n'a été démontré.

Le CSRF de l'interface est testé. Pour l'API, désactiver le CSRF et rendre la session sans état
ne suffit pas à démontrer une absence de risque si Basic est utilisé par un navigateur, comme
l'explique la [documentation Spring Security](https://docs.spring.io/spring-security/reference/features/exploits/csrf.html).
Le format JSON et l'absence d'autorisation CORS arbitraire limitent certains scénarios. **Aucune
preuve d'exploitation CSRF dans un navigateur réel n'a été produite** ; ce point reste une
question de modèle de déploiement, pas une faille exploitable affirmée.

Autres limites à planifier pour la production : absence de quotas, de limitation des tentatives
d'authentification, de pagination et de rotation des comptes. Elles ne sont pas exigées par le PDF.

## Architecture, persistance et exploitation

- Les contrôleurs REST inspectés renvoient des DTO, sans sérialisation d'entité JPA.
- `FilmService` et `SalleService` renvoient cependant des entités à leurs appelants. Cela respecte
  la frontière HTTP du PDF, mais contredit la règle interne plus stricte selon laquelle les entités
  ne franchissent jamais le service. Aligner l'implémentation ou préciser explicitement la convention.
- Les contraintes SQL de nom de salle unique, durée minimale du film et prix positif ont été
  exercées contre MySQL et rejettent les écritures invalides. L'unicité des codes et les autres
  contraintes sont présentes dans V1 ; toutes n'ont pas fait l'objet d'une nouvelle sonde individuelle.
- Le test de réutilisation remplit 20 places, annule 8 places, les réserve à nouveau, réannule
  l'ancien code, puis refuse une place supplémentaire : **total confirmé 20**, pas de double libération.
- Les index utiles aux séances et au couple séance/statut sont présents. Le filtre de titre contient
  une recherche `%texte%` ; ne pas déduire de l'existence de l'index qu'elle évite une lecture large.
  Aucun plan EXPLAIN ni test de charge n'a été exécuté.
- Le catalogue n'est pas paginé ; le dashboard compte certains éléments après chargement des listes.
  Ce sont des limites de volume, pas des défauts du périmètre minimal.
- Le wrapper est versionné, mais `mvnw` est enregistré en mode Git `100644` : la commande `./mvnw`
  nécessitera un droit d'exécution sur Unix. Windows reste le chemin effectivement vérifié.
- Le wrapper ne déclare pas de somme de contrôle de distribution. C'est une piste de durcissement
  de l'approvisionnement, pas une exigence explicite du sujet ni une compromission démontrée.

## Ordre de correction proposé

1. Rejeter les conversions numériques ambiguës, retirer les mots de passe du template, traduire
   les conflits de verrou et élargir le total par migration : A01 à A04.
2. Uniformiser les erreurs HTTP et valider les dates : A05 et A07.
3. Corriger les transitions et la publication des métriques, puis le healthcheck : A06 et A08.
4. Transformer les sondes corrigées en tests du projet, lancer `clean verify` dans le dépôt principal
   après arrêt de son JAR si nécessaire sous Windows, puis refaire le lancement hors IDE.
5. Traiter séparément la propriété des réservations et le déploiement sécurisé si un usage réel
   au-delà de l'épreuve est décidé.

## Limites de cet audit

Pas de scan exhaustif des CVE transitives, de test d'intrusion navigateur, de test de charge,
de simulation multi-JVM, de crash pendant le commit, ni d'exploration complète des deadlocks.
L'absence de constat sur ces axes n'est pas une preuve d'absence de défaut. Les 28 sondes ne sont
pas une couverture exhaustive ; elles démontrent les comportements décrits. Aucun correctif
applicatif n'a été appliqué pendant cet audit.
